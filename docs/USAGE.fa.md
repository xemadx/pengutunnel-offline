# PenguTunnel offline — v5.1.3-r3

بستهٔ نسخه‌بندی‌شده برای Linux x86_64 با نصاب Bash خوانا، منوی CLI، کنترل SHA-256 و آزمون دو سمت شبکهٔ ایزوله. این انتشار بر پایهٔ هستهٔ مشخص **v5.1.3** است و مشکل مسیر دادهٔ DNS را اصلاح می‌کند.

## نصب تک‌خطی روی هر دو سرور

روی Ubuntu/Debian دارای systemd فعال، در ترمینال تعاملی اجرا کنید:

```bash
curl -fsSL --proto '=https' --tlsv1.2 https://github.com/xemadx/pengutunnel-offline/releases/latest/download/install.sh | sudo bash
```

منوی نصب همان‌جا باز می‌شود. اگر از قبل با root وارد شده‌اید، این شکل هم کار می‌کند:

```bash
bash <(curl -fsSL --ipv4 https://github.com/xemadx/pengutunnel-offline/releases/latest/download/install.sh)
```

نصاب هسته و manager متعلق به **یک تگ مشخص** را از Releases می‌گیرد و هش هر دو را پیش از اجرا کنترل می‌کند. در صورت در دسترس نبودن asset، فقط همان تگ را از raw GitHub می‌گیرد؛ سراغ باینری upstream یا نسخه‌ای با هش نامعلوم نمی‌رود. دریافت اولیه به اینترنت و `curl` نیاز دارد؛ نصب پیش‌نیازهای ناقص ممکن است به مخزن سیستم‌عامل نیاز داشته باشد.

برای نصب نسخهٔ ثابت، به‌جای `main` تگ را بنویسید:

```bash
curl -fsSL https://raw.githubusercontent.com/xemadx/pengutunnel-offline/v5.1.3-r3/install.sh | sudo bash
```

فایل‌ها در `/opt/pengutunnel-offline/releases/<TAG>` حفظ می‌شوند. بازکردن دوبارهٔ منو و نصب مجدد هسته به پوشهٔ موقت حذف‌شده وابسته نیست:

```bash
sudo pengu
```

## تنظیم دو سمت

1. روی ایران، گزینهٔ **۱ → Iran**؛ روی خارج، گزینهٔ **۱ → Kharej** را انتخاب کنید.
2. نوع transport، جهت، رمزنگاری و پورت حامل را در دو سمت هماهنگ کنید. پورت حامل روی سمت شنونده باید قابل دسترسی باشد.
3. یک **PSK قوی و یکسان** روی هر دو سمت بگذارید. اگر روی ایران PSK خودکار ساختید، همان را روی خارج وارد کنید. PSK همچنان برای احراز هویت لازم است.
4. پورت‌های کاربران را روی ایران تعریف کنید؛ سرویس مقصد باید روی خارج واقعاً گوش بدهد. PROXY protocol را فقط وقتی فعال کنید که سرویس مقصد هم آن را پشتیبانی کند.

برای TCP از `tcpfwd / reverse` شروع کنید. برای UDP یا WireGuard، مسیر TUN مانند `PGprotocol-NUM3` یا IPX را انتخاب کنید. L4 و DNS/SSH را به‌عنوان فوروارد UDP معرفی نمی‌کنیم.

در TUN، پیش‌فرض‌ها `10.20.0.1/24` و `10.20.0.2/24` هستند. برای تانل دوم، **نام رابط، subnet، health port و پورت شنوندهٔ مجزا** انتخاب کنید. نصاب تعارض health port، نام رابط و IP را بررسی می‌کند. برای IPهای داخلی سفارشی، مقصد فوروارد صریح تعیین می‌شود.

DNS این build فقط **IPv4** است. اصلاح r3 اجازه نمی‌دهد سوکت dual-stack با فرستندهٔ گروهی IPv4 ترکیب و مقصد داده به `0.0.0.0` تبدیل شود.

## به‌روزرسانی با تگ

روی هر دو سرور:

```bash
sudo pengu update
```

یا یک انتشار مشخص:

```bash
sudo pengu update v5.1.3-r3
```

فرمان update بدون آرگومان، bootstrap آخرین ریلیز منتشرشده را می‌گیرد؛ با تگ، asset همان ریلیز را دریافت می‌کند؛ هر bootstrap هش و شمارهٔ بستهٔ خودش را دارد. بازگشت با این فرمان برای تگ‌های دارای bootstrap نسخه‌بندی‌شده، از r3 به بعد، پشتیبانی می‌شود. پیش از تغییر نسخهٔ هسته، هر دو سمت را هماهنگ کنید. انتخاب مجدد همان شناسهٔ تانل، تأیید جایگزینی می‌خواهد، کانفیگ قبلی را پشتیبان می‌گیرد و سرویس فعال را restart می‌کند.

آپدیت پس‌زمینهٔ upstream خاموش است. گزینهٔ **۵** فقط keeper محلی را مدیریت می‌کند؛ keeper دانلود انجام نمی‌دهد. گزینهٔ **۶** هستهٔ همین بستهٔ بررسی‌شده را دوباره نصب می‌کند.

## بررسی، نصب محلی و تست

پس از دریافت مخزن یا فایل tar.gz انتشار:

```bash
python3 tools/check_package.py
bash install.sh --verify-only
sudo bash install.sh
```

`--verify-only` فایل‌ها را بررسی می‌کند و سرویس یا نصب را تغییر نمی‌دهد. برای بازاجرای آزمون کامل روی Linux/WSL دارای cgroup v2، namespace، iproute2، TUN و libseccomp:

```bash
sudo bash tests/run-isolated.sh /var/tmp/pengu-test-results
```

آزمون دو namespace جدا با IPهای `10.203.0.1` و `10.203.0.2` و یک veth می‌سازد. پردازش‌ها اینترنت ندارند، سورس/ابزارها فقط‌خواندنی‌اند و نوشتن، حافظه، CPU، تعداد پردازش و زمان محدود است. آزمون نصاب از systemctl ساختگی استفاده می‌کند؛ سرویس واقعی میزبان را نصب یا تغییر نمی‌دهد.

پوشش شامل شش L4 در direct/reverse، AES-GCM/ChaCha/none، PSK اشتباه، TUN با TCP/UDP/PGprotocol/DNS/SSH، dualway، شش IPX، source spoof محلی، SNI spoof محلی، چند اتصال هم‌زمان و بازیابی با supervisor است. خلاصهٔ اجرای ثبت‌شده و حدود شواهد در [گزارش r3](docs/AUDIT-R3.fa.md) است.

**این آزمون، تضمین نبود همهٔ باگ‌ها یا عبور از فیلترینگ واقعی نیست.** CDN واقعی، NAT و فایروال دیتاسنتر، DPI اینترنت ایران، اجرای چندساعته و نصب کامل روی سرور تولید از تست محلی نتیجه نمی‌شوند. `alive=true` به‌تنهایی نیز جای تست انتقال داده را نمی‌گیرد.

## سورس، هسته و منشأ

bootstrap، آزمون‌ها، ابزار انتشار و دستور اصلاح DNS تحت MIT و قابل مطالعه‌اند. **سورس اصلی هسته در این مخزن وجود ندارد**؛ هسته یک ELF اصلاح‌شده است و از روی سورس اصلی کامپایل نشده است. مجوز MIT، باینری upstream یا بخش‌های متعلق به upstream را متن‌باز نمی‌کند؛ [جزئیات مجوز](NOTICE.md) را ببینید.

سرور رسمی در بررسی ۲۰۲۶-۱۱-۰۲، `v5.1.7` عرضه می‌کرد؛ نصاب رسمی همچنان `4.2.6` بود و صفحهٔ راهنما نمونه‌های قدیمی‌تری داشت. دریافت و دی‌کامپایل بخش DNS نسخهٔ جدید، به معنی مهاجرت این انتشار به آن نیست. این بسته عمداً نسخهٔ آزموده‌شدهٔ مشخص خود را نصب می‌کند.

- [ممیزی و اصلاحات r3](docs/AUDIT-R3.fa.md)
- [ساختار هسته](docs/ARCHITECTURE.fa.md) و [schema تنظیمات](docs/CONFIG-STRUCTURE.fa.md)
- `tools/patch_core.py`: بازتولید اصلاح DNS از **r2 دقیق با هش ورودی مشخص**؛ روی فایل نسخهٔ دیگری اجرا نمی‌شود.
- `tools/build_offline.py` و شواهد قبلی، مربوط به ساخت اولیه و گزارش‌های تاریخی‌اند.
- `evidence/`: شواهد غیرمحرمانه؛ شامل کلید، توکن حساب یا کانفیگ واقعی سرورها نیست.

## انتشار نسخهٔ بعدی

پس از تغییر، آزمون و به‌روزرسانی مستندات:

```bash
python3 tools/update_manifest.py --version v5.1.3-r4
python3 tools/check_package.py
sudo bash tests/run-isolated.sh /var/tmp/pengu-r4-results
git add .
git commit -m "Release v5.1.3-r4"
git tag v5.1.3-r4
git push origin main v5.1.3-r4
```

Workflow تگ را تست می‌کند، بستهٔ قابل بازتولید می‌سازد، assetها و SHA256SUMS را بارگذاری می‌کند و پس از تکمیل آن‌ها Release را منتشر می‌کند. این کار **بسته‌بندی باینری بررسی‌شده** است؛ ادعای کامپایل هستهٔ upstream ندارد. بررسی SHA جای اعتماد به bootstrap اولیه و حساب انتشار را نمی‌گیرد.
