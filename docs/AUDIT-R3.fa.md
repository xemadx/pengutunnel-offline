# ممیزی عملکرد و اصلاحات r3

تاریخ: ۲۰۲۶-۱۱-۰۲. موضوع این انتشار، هستهٔ مشخص v5.1.3 و نصاب مشتق از 4.2.6 است. این گزارش، بررسی عملکرد و آزمون محلی است؛ گواهی ممیزی جامع امنیت یا نبود تمام نقص‌ها نیست.

## نتیجهٔ قابل بازتولید

۱۴۰ سناریوی سطح بالا در WSL2/Ubuntu 24.04 گذشتند. این تعداد شامل ۱۳۷ سناریوی ماتریس و ۳ سناریوی تکمیلی PROXY v2/CLI است؛ helperهای نصاب جداگانه ۲۰ بررسی parity و ۲۱ بررسی regression دارند. ۶۸۳ بررسی انتقال موفق، مجموعاً ۱۵۳٬۲۸۵٬۲۰۳ بایت payload را بررسی کردند. خلاصه در `evidence/r3-test-summary.json` است؛ سناریوهای رد اتصال، عمداً انتقال موفق ندارند.

دو namespace شبکهٔ مستقل، veth و IPهای `10.203.0.1/30` و `10.203.0.2/30` به کار رفتند. رابط‌های داخلی TUN از subnet دیگری بودند. فرآیندهای هدف خارج از این شبکه مسیری نداشتند. فایل‌های پروژه و ابزارها فقط‌خواندنی و فضای نوشتن tmpfs محدود بود؛ cgroup سقف حافظهٔ ۱ GiB، swap صفر، ۱۹۲ task و دو CPU داشت. syscallهای خروج از محیط، دسترسی vsock و ابزارهای kernel مسدود بودند. پردازش‌های موتور با uid 65534 و فقط قابلیت‌های شبکهٔ لازم برای TUN/raw اجرا شدند.

آزمون bootstrap یک PTY تازه داشت، ورودی pipe را واقعاً خواند، فایل‌ها و CLI را با uid صفر در فایل‌سیستم ایزوله نصب کرد و منو را دوباره باز کرد. `systemctl` و `dpkg` در این آزمون fixture بودند؛ systemd واقعی یا سیستم میزبان تغییر نکرد.

## ۱. خرابی مسیر دادهٔ DNS — اصلاح هسته

**قبل:** در direct و reverse، احراز هویت موفق و `/health` برابر HTTP 200 با `alive=true` بود؛ اما حتی echo یک بایت و ping داخل TUN شکست می‌خورد. MTU=1000، دامنهٔ DNS صریح و انتظار بیشتر نیز مشکل را رفع نکردند. شمارندهٔ TUN سمت مقصد دریافت داده را نشان نمی‌داد.

**علت:** شنونده با network=`udp` و آدرس `0.0.0.0` سوکت dual-stack می‌ساخت. مسیر ارسال گروهی DNS، آدرس IPv4 و ساختار `sockaddr_in` انتظار داشت. در trace فرآیند متعلق به همین آزمون، syscall شمارهٔ 307 یعنی `sendmmsg` موفق برمی‌گشت، ولی مقصد آن `0.0.0.0:<peer-port>` بود. پیام «مشکل از سرور خارج است» در این وضعیت تشخیص درستی نبود.

**کنترل مستقل:** فقط تغییر bind به IPv4 مشخص، بدون دست‌کاری باینری، هر دو جهت را از شکست به انتقال صحیح ۱ بایت تا ۱ MiB رساند.

**اصلاح:** دو آرگومان ResolveUDPAddr/ListenUDP در تابع `0x18db360` صریحاً `udp4` شدند. literal ثابت در padding بدون استفاده قرار گرفت؛ طول فایل، توابع، call siteها، stack frameها و stack mapهای Go تغییر نکردند. پنج محدوده بازنویسی شد؛ دستور بازتولید با پیش‌شرط هش و بایت‌های ورودی در `tools/patch_core.py` است. این اصلاح فقط برای همین build است و DNS این انتشار را IPv4 می‌کند.

**بعد:** همان wildcard و همان تنظیمات قبلی در direct/reverse، با AES-GCM و ChaCha، انتقال سالم داشتند. سایر transportها روی همان فایل اصلاح‌شده در ماتریس بررسی شدند. شواهد: `r3-dns-patch.json`، `r3-dns-before-after.json` و `r3-dns-syscalls.json`.

## ۲. باگ‌های نصاب و اصلاح آن‌ها

| نقص بازتولیدشده | اصلاح |
|---|---|
| هشدار نبود fail2ban/iptables داخل بلوک redirectشده نوشته و TOML را خراب می‌کرد | warning به stderr رفت؛ خروجی هر دو نقش با parser TOML بررسی شد |
| ساخت دوبارهٔ همان شناسه، فایل را عوض می‌کرد ولی `enable --now` سرویس فعال را restart نمی‌کرد | جایگزینی صریح، backup و restart سرویس فعال؛ شکست start به caller برمی‌گردد |
| health port نامعتبر یا تکراری پذیرفته می‌شد | کنترل عدد ۱ تا ۶۵۵۳۵، تکرار سؤال نامعتبر و منع تعارض با کانفیگ دیگر |
| quote/backslash در PSK، TOML نامعتبر می‌ساخت | helper مشترک escape رشته؛ مقدار اصلی پس از parse حفظ می‌شود |
| EOF پس از ورود فوروارد به‌جای لغو، کانفیگ ناقص را ثبت می‌کرد | شکست read قبل از نوشتن و فعال‌کردن سرویس برمی‌گردد |
| شمارهٔ صفر در ban-sync به index منفی Bash و آخرین تانل تبدیل می‌شد | کنترل بازهٔ انتخاب قبل از دسترسی آرایه |
| IPهای TUN سفارشی مانند `.10/.11` با فوروارد کوتاه قابل حدس نبودند | سؤال مقصد داخلی و نوشتن `PORT=IP:PORT` صریح؛ انتقال واقعی نیز بررسی شد |
| فایل manager از پوشهٔ موقت اجرا و سپس حذف می‌شد | نگهداری بستهٔ مشخص در `/opt` و CLI دائمی؛ بازکردن مجدد منو تست شد |
| نبود package manager می‌توانست موفقیت پیش‌نیازها تلقی شود | کنترل ابزارهای لازم و شکست صریح؛ خطای نصب بسته نیز متوقف می‌کند |
| نسخهٔ نصب‌شدهٔ صحیح دائماً «update available» دیده می‌شد | تفکیک نسخهٔ بسته از نسخهٔ واقعی core |
| mirror با HTTP ناموفق به‌عنوان سریع‌ترین انتخاب می‌شد | استفاده از `curl --fail` و رد پاسخ ناموفق |
| DNS benchmark فقط بازبودن TCP/53 را می‌سنجید | درخواست واقعی DNS و نیاز به جواب A؛ این ابزار اختیاری به `dig` نیاز دارد |
| جایگزینی/restore تنظیمات DNS می‌توانست فایل قبلی را پیش از موفقیت حذف کند | نوشتن در فایل موقت و rename؛ بدون backup تنظیم حدسی اعمال نمی‌شود |
| restore مخزن می‌توانست پس از شکست cp موفقیت چاپ کند | جایگزینی موقت، کنترل خطا و حفظ فایل قبلی |

به علت ماهیت systemd، آزمون محلیِ نصاب از backend ساختگی استفاده می‌کند. این شواهد برابر با نصب کامل root روی یک VPS واقعی نیستند.

## ۳. ماتریس موتور

- `tcpfwd/tls/ws/wss/xhttp/xhttps` × direct/reverse × AES-GCM/ChaCha/none: انتقال سالم.
- PSK متفاوت در هر شش نوع و هر سه تنظیم رمزنگاری: انتقال رد شد.
- هدرهای NUM1/NUM2/NUM3، fingerprintهای پنج‌گانه، pool=4 با هشت کاربر هم‌زمان، half-close و TCP Forward روی IPv6: موفق.
- TUN روی TCP، UDP، سه PGprotocol، DNS و SSH، در دو جهت و با دو cipher: موفق. DNS/SSH فوروارد UDP ندارند؛ آن را به تست تحمیل نکردیم.
- TCP/UDP dualway؛ شش IPX با دو cipher؛ شش IPX با source spoof محلی؛ SNI spoof روی TLS/WSS/XHTTPS محلی: موفق.
- PROXY v2 روی L4 و TUN: backend سرآیند را اعتبارسنجی و payload را صحیح دریافت کرد.
- link flap، kill سمت مقابل، supervisor محدود و بازگشت انتقال روی TCP/WS/XHTTP: موفق. خروج با کد ۱ پس از پیام restart طرف مقابل، رفتار نیازمند supervisor است؛ آن را به‌تنهایی باگ reconnect نام‌گذاری نکردیم.

اختلاف دو هدر شماره‌دارِ شناخته‌شده الزاماً اتصال را رد نکرد؛ تشخیص هدر در این build انعطاف دارد. این رفتار، PSK را دور نمی‌زند. اشتباه در انتظار اولیهٔ آزمون، از باگ موتور جدا شد. کمبود `awk` در chroot، سقف اولیهٔ ناکافی کپی ELF و fixture اولیهٔ backend UDP نیز اصلاحات harness بودند و در شمار باگ‌های محصول نیامدند.

## ۴. دامنهٔ استخراج هسته

تمام `.text` هستهٔ r3، شامل **۶٬۷۹۷٬۱۰۱ دستور** و جدول **۴۲٬۲۲۰ تابع** استخراج شد. فقط ۶٬۴۴۵ ورودی نام غیرخالی دارند. خروجی اسمبلی کامل، فهرست تابع‌ها و SHA هسته به assetهای Release افزوده می‌شوند. `tools/export_engine.py` ابزار بازتولید این استخراج است.

۲۴ تابع مسیر DNS نسخهٔ مبنا با Ghidra دی‌کامپایل شد؛ فایل‌های منتخب شاهد در `evidence/r3-dns-decompiled` هستند. این خروجی‌ها، pseudo-C با نوع‌ها/ABI ناقص‌اند و سورس Go قابل‌بیلد معرفی نمی‌شوند. استخراج تمام دستورها با فهم معنایی تمام توابع یکی نیست؛ سورس اصلی، وابستگی‌های کامل و اطلاعات کامپایل از این فایل قابل بازیابی قطعی نبود.

## ۵. تطبیق با منبع رسمی جدید

[راهنمای رسمی](https://pg.pengucloud.net/) و نصاب ارسالی دریافت شدند. صفحهٔ اصلی، panelها و templateهای راهنما را در همان HTML دارد؛ متن و templateها بررسی شدند. درخواست مستقیم برخی مسیرهای داخلی پاسخ 403 داشت؛ از آن‌ها ادعای دریافت مستقل نمی‌کنیم. نصاب gzip/base64 بدون اجرای eval باز شد و دقیقاً با capture قبلی 4.2.6 برابر بود.

سرور رسمی اکنون v5.1.7 عرضه می‌کرد. فایل packed برابر با SHA منتشرشده بود، UPX آن در محیط ایزوله باز شد و ۴۲٬۲۵۳ ورودی تابع استخراج شد. ۲۴ تابع متناظر DNS نیز جداگانه دی‌کامپایل شدند. الگوی network=`udp` و batch IPv4 در این تحلیل استاتیک دیده شد؛ تست انتقال و ادعای اصلاح نسخهٔ لایسنس‌دار 5.1.7 انجام نشده است. offsets یا patch نسخهٔ 5.1.3 به آن اعمال نشدند.

این انتشار خودسرانه به نسخهٔ جدید مهاجرت نمی‌کند. manifest و فرمان نصب دقیقاً core آزموده‌شدهٔ r3 را انتخاب می‌کنند.

## حدود باقی‌مانده

CDN واقعی، DPI و شبکهٔ واقعی ایران/خارج، NAT/فایروال دیتاسنتر، پایداری چندساعته، بار ظرفیت، ban-sync واقعی با x-ui/fail2ban و بررسی جامع رمزنگاری مستقل هنوز تأیید نشده‌اند. آزمون local با source spoof فقط عملکرد مسیر ساخت/خواندن بسته در شبکهٔ آزمایش را نشان می‌دهد؛ عبور spoof از دیتاسنتر را اثبات نمی‌کند. مجوز اجزا در `NOTICE.md` مشخص شده است؛ این مخزن هستهٔ کاملاً متن‌باز را ادعا نمی‌کند.
